> **${var}** — Optional focus area (e.g. `"fix sandbox curl failures"`, `"improve notification formatting"`). If empty, derives improvement targets from recent performance data automatically.

Today is ${today}. Read `memory/MEMORY.md` for current goals and active topics.

## Overview

Reads recent `memory/logs/`, `memory/issues/`, and skill run history to identify the lowest-performing or most-broken skills. Proposes specific, targeted improvements — better prompts, fixed sandbox patterns, improved error handling — and opens PRs via `gh` CLI. Never touches `vigil.yml` schedules or enables/disables skills.

---

## Steps

### 1. Gather performance data

**From memory logs (last 14 days):**

```bash
ls memory/logs/*.md | sort -r | head -14
```

Read each log file. Extract:
- Skills that logged `ABORTED`, `FAILED`, `ERROR`, or `no data` outcomes
- Skills that ran successfully but produced thin output (e.g. "0 items", "empty result")
- Skills that logged warnings or fallback-path activations (e.g. "WebSearch fallback used")

Build a frequency table: `skill_name → {failures, warnings, empty_outputs, successes}`.

**From memory issues:**

Read `memory/issues/INDEX.md` if it exists. Extract open issues (status: `open`, `investigating`, `fixing`). Note affected skills and categories.

**From cron state (if available):**

```bash
cat cron-state.json 2>/dev/null || echo "{}"
```

Extract last-run timestamps and any stored failure counters.

**From `${var}`:**

If `${var}` is set, add the described focus area to the target list as high priority.

### 2. Rank improvement targets

Sort skills by improvement urgency:

| Priority | Condition |
|----------|-----------|
| P1 | 3+ failures in last 14 days, OR open critical/high issue |
| P2 | 2 failures or 3+ warnings in last 14 days |
| P3 | 1 failure or empty output >50% of runs |
| P4 | No failures but known pattern improvement (from `${var}` or community patterns) |

Pick the top 3 targets (P1 first, then P2, etc.).

If zero targets identified (everything is green), log and stop:
```
### self-improve
- All skills healthy — no improvements queued
```
Notify briefly. Stop.

### 3. Analyze each target skill

For each target skill, read its `skills/${skill_name}/SKILL.md` in full.

Diagnose the root cause by cross-referencing:
- The failure pattern from logs (what error message or symptom appeared?)
- The SKILL.md instructions (does it handle the failure case? is the sandbox note accurate?)
- The category from the issues index (known issue type?)

Common failure patterns and their fixes:
- **`curl: (6) Could not resolve host`** → skill is using curl without WebFetch fallback; add explicit fallback
- **`jq: parse error`** → JSON parsing without null guard; add `// empty` or error check
- **`No data found`** → API endpoint changed; update URL or add alternative source
- **Thin output / always empty** → search query too narrow or date filter too strict; widen parameters
- **Rate limit (429)**  → no backoff logic; add retry with 5s delay
- **Notification too long** → message exceeds Telegram 4096-char limit; add truncation

### 4. Draft improvements

For each target skill, draft a specific diff:

- Identify the exact lines in SKILL.md that cause or miss the failure
- Write the improved version of those lines
- Do not rewrite the entire SKILL.md — surgical changes only
- Do not change the skill's `name`, `description`, or fundamental purpose
- Do not add steps that change the skill's scope

Document the change as:
```
Skill: ${skill_name}
Problem: ${one-line description of the failure pattern}
Root cause: ${why it fails}
Fix: ${what is being changed and why}
Lines affected: ~${line_range}
```

### 5. Create a branch and apply changes

```bash
git checkout -b self-improve/${today}-${skill_name} main
```

Apply the improvements to each target skill's SKILL.md. Make minimal, targeted edits — do not touch formatting or sections unrelated to the fix.

Stage and commit each skill separately for reviewability:

```bash
git add skills/${skill_name}/SKILL.md
git commit -m "fix(${skill_name}): ${one-line description of the fix}"
```

### 6. Open pull requests

Open one PR per improved skill (easier to review individually):

```bash
gh pr create \
  --title "fix(${skill_name}): ${problem_summary}" \
  --body "## Problem
${problem_description}

## Root Cause
${root_cause}

## Fix
${fix_description}

## Evidence
$(relevant log lines or issue reference)

Auto-generated by self-improve on ${today}." \
  --base main \
  --head self-improve/${today}-${skill_name}
```

Record the PR URL.

### 7. Log and notify

Append to `memory/logs/${today}.md`:
```
### self-improve
- Targets analyzed: ${target_count}
- PRs opened: ${pr_count}
$(for each PR: "- PR: ${pr_url} — ${skill_name}: ${problem_summary}")
$(if zero improvements): - No improvements needed — all targets healthy
```

```
./notify "*Self Improve — ${today}*

${pr_count} PR(s) opened for skill improvements.

$(for each PR): - [${skill_name}](${pr_url}): ${problem_summary}

$(if issues_referenced): Related issues: ${issue_ids}

Review and merge to apply."
```

---

## What self-improve does NOT do

- Does not modify `vigil.yml` — the operator controls schedules, cron, and which skills are enabled
- Does not enable or disable skills
- Does not change memory structure, log formats, or notification routing
- Does not upgrade dependencies or package.json
- Does not open PRs that are entirely rewritten skills (only surgical fixes)

---

## Required secrets

None beyond standard `gh` CLI auth (already configured for GitHub Actions via `GITHUB_TOKEN`).

---

## Sandbox note

All operations are local: reading files, writing edits, and running `git` and `gh` commands. No external API calls needed. `gh pr create` uses the `GITHUB_TOKEN` from the Actions environment — no manual auth setup required.

## Constraints

- Maximum 3 skills improved per run to keep PRs focused and reviewable.
- Never directly push to `main` — always open a PR.
- Never modify `vigil.yml` or any file outside `skills/`.
- Improvements must be grounded in actual evidence from logs or issues — no speculative refactors.
- One PR per skill, not one omnibus PR.
